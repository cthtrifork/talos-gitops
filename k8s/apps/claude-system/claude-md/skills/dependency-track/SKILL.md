# Dependency-Track: query and assess

`$DT_URL` and `$DT_API_KEY` are already in the pod (PR #1021, team `claude-triage`). Never print or copy the key; pass it as
`-H "X-Api-Key: $DT_API_KEY"`. Check with `[ -n "$DT_API_KEY" ] && echo set`. Unset: the config CronJob has not made the key yet or the pod needs a restart; ask.

- Permissions: view portfolio and vulnerabilities, read/create/update analysis. No BOM upload, no admin.
- Projects are workload containers (name `namespace/repository`, version = image tag; a new tag is cloned from the previous version with its audit history): `curl -s -H "$H" "$DT_URL/api/v1/project?pageSize=100&pageNumber=1"`. Lists and findings return 100 rows per page (`X-Total-Count` has the total): loop over `pageNumber`, `limit` is ignored. Only some images are tracked, so a CVE in Trivy can be absent here: say so.
- A CVE: `GET /api/v1/vulnerability/source/NVD/vuln/<id>` (severity, CVSS, EPSS) and `.../projects` for the affected projects.
- Findings of a project: `GET /api/v1/finding/project/<uuid>?pageSize=100&pageNumber=N` (project `metrics.critical` matches the findings once paged). `searchText` on `/api/v1/finding` does not filter by CVE; do not trust it.
- Record an assessment: `PUT /api/v1/analysis` with `project`, `component`, `vulnerability` uuids, `analysisState`, `analysisJustification`, `analysisDetails`, `suppressed`.
  Only after the owner agrees. `NOT_AFFECTED`, `FALSE_POSITIVE` and `RESOLVED` end up in the daily VEX export PR.
- Assess from the data: DT severity and EPSS vs Trivy's, whether the vulnerable component (e.g. `sshd` vs a client-only package) is in the image, and whether a fix exists. Say what you did not verify.
- Trivy in-cluster: `kubectl get vulnerabilityreports -A` (summary `criticalCount`; the same CVE repeats per package).
- The Trivy report decides what to assess (`kubectl get vulnerabilityreport -n <ns> <name> -o json`, `.report.vulnerabilities`); it is already filtered (ignore policy, `trivyignore.yaml`, vendor `not_affected`/`will_not_fix`, VEX). DT holds more findings and is the metadata and the interface to record assessments: match on `(vulnId, component name)` and take the component and vulnerability uuids from the DT finding. DT findings missing from Trivy are not assessed.
- Consider usage first: what this cluster actually uses decides applicability, not the CVE title. Grep the repo (`git grep -i <feature>` in `k8s/`, the app README and values) for the feature behind the package (Kerberos/GSSAPI, Ceph, SSH, DTLS, image decoders, ...). Unused in every image: `trivyignore.yaml` PR with the reason, never a DT record (a server-only title such as KDC or kadmind is the wrong reason when the whole feature is unused). Unused in this image only: `NOT_AFFECTED` with `CODE_NOT_PRESENT` or `CODE_NOT_REACHABLE`. Used, or unclear: leave it open and say so. Never record one only because the risk is low, and never from title guesses or from an exposure claim you did not check (check it, or leave the finding open).
- Go dependency CVE (`golang.org/x/*`, stdlib): run the `govulncheck` skill first. Symbol absent from the binary: `NOT_AFFECTED` / `CODE_NOT_PRESENT`; present or not checked: use the exposure rule below, or leave it open.
- Exposure from network policies: when asked to assess, or when the code path is unknown, read the CiliumNetworkPolicies first (`kubectl get ciliumnetworkpolicy -n <ns> -o yaml`) and the pod spec (`hostNetwork`). Default deny, ingress only from kube-apiserver, host or cluster, and egress only to named hosts (no untrusted input reaches the binary): after the owner agrees, record `NOT_AFFECTED` with `PROTECTED_BY_MITIGATING_CONTROL`, but only for a flaw the policy actually blocks (UDP/QUIC, non-443 ports, a server the pod does not run); a client-side or library flaw reachable from the allowed hosts or a path on the network is not blocked by it, so verify the code path instead. Leave open: LAN or world ingress (`fromCIDR`, `world`), `hostNetwork` pods (Cilium policies do not apply), open internet egress, tools that process input you choose, namespaces whose policy you did not read, and projects whose DT version is not the live tag. Do not answer "cannot assess" when this evidence exists: do it, or list what is missing.
- Workflow when asked to assess (the request is the owner's agreement; do not ask again per step or per project):
  1. List the affected projects (`.../vuln/<id>/projects`) and keep the live tags from the running pods; read the Trivy row for the same image.
  2. Gather evidence per image in this order: unused everywhere (trivyignore), Go CVE (`govulncheck` skill), exposure (below).
  3. Record every project that meets the rules in the same turn, then give one summary: recorded (with the evidence), left open (why).
- A record is a verified conclusion: never record and then say "not verified" (in `analysisDetails` or the summary). Find the evidence first; when
  it cannot be found, leave the finding open. `analysisDetails` is written per vulnerability: what the flaw is, what an attacker needs, and the
  checked fact that stops it (a source line, a Dockerfile line, a policy rule, a govulncheck result), not one text copied to every row.
- Ways to verify, in order: `govulncheck` (map CVE to GO id via `vuln.go.dev`; symbol absent is `CODE_NOT_PRESENT`; a GO id with no entry cannot be checked, so leave it open);
  the project's source at the live tag (`git clone --depth 1 --branch <tag>` into its own directory: image build flags such as `CGO_ENABLED`, `apk add` lines, `os/exec`, listeners, `grpc.NewServer`,
  TLS use); `image-files` (see `image-inspect`) for what the image ships, e.g. whether a script imports the vulnerable package; the Kustomization or Helm values for the feature; then network policy. Delete the clone afterwards. Distro libraries (curl, expat, pcre2, zlib) a static Go binary does not load are
  reachable only through child processes: check which ones the code starts and whether this cluster triggers them.
- Read every place the image's code runs a program, not a sample: `git grep -n -E 'exec\.Command|CommandContext|exec\.|mount\.New'` in `cmd/` and `pkg/` (startup code in `cmd/main.go` too, and library wrappers such as k8s mount-utils that run `mount`, `umount`, `findmnt`),
  and the image's `ENTRYPOINT`. Read the condition before saying a path is "only for X" (an edition, a mode): a startup call has none. A wrong claim in a record is withdrawn or corrected the same turn.
- Distro packages: first list every program that runs (source exec calls, the entrypoint, what a launcher script `exec`s at its end, e.g. a downloaded client binary) and run `image-files needed` on each: a `static` binary loads nothing, a dynamic one names its libraries. Do not assume a binary is static or that a named package is the only dependency. Then read `/var/lib/dpkg/status` with `image-files` (`IMAGE_FILES_MAX=4194304`) and compute the `Depends` closure of the programs that run (plus what an interpreter loads for the imports the script makes: `ssl` loads libssl3, `gzip` loads zlib1g). A package outside the closure is never loaded:
  `CODE_NOT_REACHABLE`, with the flaw from the DT description and the closure fact. A package inside the closure needs its own per-CVE analysis (what the flaw needs, whether the program does it), or stays open.
- A library flaw matters only if a program that runs imports the vulnerable function: `image-files symbols <image> '<egrep of the function names>'` lists the importers; compare them with the programs that run (`PKCS7_`/`CMS_` for OpenSSL CMS flaws, `DTLS` for DTLS, `gzwrite` for zlib gz writes, `pcre2_dfa_match`/`pcre2_jit` for PCRE2, `acl_get_file` for libacl).
- Read the launcher of an interpreted entrypoint with `image-files cat` (which interpreter `PATH` picks, its imports) before judging Python/Perl packages; Debian's `python3-*` packages are invisible to the slim image's `/usr/local/bin/python3`.
- After a batch of `PUT /api/v1/analysis`, read a sample back (`GET /api/v1/analysis?project=&component=&vulnerability=`) and say so. Keep large JSON out of environment variables (`Argument list too long`): pipe it or ask `kubectl -o jsonpath` for the two fields needed.
- Clone sources into the session scratchpad, not `/workspace`: a safety check blocks `rm -rf` of a `/workspace` directory, so the clone could not be deleted. Ask for `urlshare` approvals as soon as a page is needed, in the same turn as the other work.
- Rules apply to every record already written: when a new rule or a mistake shows an earlier record broke it (a client-side flaw recorded on a policy basis), withdraw or fix it and say so.
- Set `TMPDIR` to the session scratchpad when running `govulncheck-image` (it is unset and the script falls back to `/tmp`).
  4. Anything that needs a permission or a tool you lack: say which, do the rest, do not reach around it.
- Exposure is more than the CiliumNetworkPolicy: also read the Services (`LoadBalancer`, `NodePort`), IngressRoutes and the pod's `hostNetwork`.
  A Service can expose more than its name says (`prometheus-otlp-lb` reaches the whole Prometheus HTTP API from the LAN).
  Never write an exposure claim ("never parses untrusted HTML") without that evidence; without it, leave the finding open.
- Go CVE to GO id: `curl -s https://vuln.go.dev/ID/<GO-id>.json` (`aliases`, `affected[].ranges`, `imports[].symbols`). A GO finding that DT does not hold needs no record.
  `govulncheck -mode=binary` lists a vulnerability under "Symbol Results" only if a vulnerable symbol is in the binary: absent is `CODE_NOT_PRESENT`
  (confirm with `-show verbose` when that is the basis of a record).
- Findings on the scanned app's own module (Prometheus, kubectl, ...) can be false positives: the main module has no version, so govulncheck uses a
  pseudo-version `v0.0.0-<date>-<commit>` that sorts below every release. Compare the build commit with the advisory's fix (`gh api repos/<owner>/<repo>/compare/<fix>...<tag>`,
  `behind_by` 0 means contained) and the release number with the ranges (Prometheus `3.N.x` is module `v0.3NN.x`) before calling one real.
- Decisions made on an older tag: the clone keeps a decision only for a component whose version did not change, so a bumped package (`x/net` v0.56 to v0.57) comes back open in the new tag. When asked to assess an image that already has decisions, compare the previous version of the project (`GET /api/v1/project?name=...`, next newest) with the latest: for each open finding on the latest with a `NOT_AFFECTED` or `FALSE_POSITIVE` decision for the same vulnerability and the same package name on the previous version, check that the basis still holds on the new version (`govulncheck` skill for a Go symbol, the exposure evidence above for network policy) and record it on the latest. Say `Carried from <old tag>` in `analysisDetails` and what you re-checked. Never copy `RESOLVED`, never copy when you could not re-check, and list what you carried and what you left open in the summary.
- Old versions stay in DT until the retire job removes them: take the live tag from the running pods (`kubectl get pods -A`). A project can also lag (no SBOM yet for the live tag): say so.
- DT severity is NVD's. For distro packages (deb, apk) Debian and Alpine rate many CVEs lower and have no fix: compare with Trivy (`vulnerabilityreports`: `severity`, `fixedVersion`).
- Conventions, in this order:
  1. A CVE that is not applicable to any image (wrong product, other OS, feature never used) goes in `k8s/infra/trivy-system/trivy-operator/ignore/trivyignore.yaml` (PR) and is not also assessed here.
  2. A finding that is not applicable to this image only (the component is present but the vulnerable code is not used or reachable) is assessed here as `NOT_AFFECTED` (with `analysisJustification`) or `FALSE_POSITIVE`, even when a bump would fix it. It reaches the VEX export PR.
  3. A finding that applies, whether or not a fix exists, is not assessed: it stays open (a fix is a bump).
- DT has no delete for an analysis: withdraw one with `analysisState` and `analysisResponse` `NOT_SET`. Reading one: `GET /api/v1/analysis?project=&component=&vulnerability=`.
